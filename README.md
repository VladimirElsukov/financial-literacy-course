# Оркестратор курса «Финансовая грамотность»

Этот файл — главная инструкция для агента-оркестратора.
Агент должен следовать ей при выполнении любых задач в этом проекте.

## Роли и задачи

- **Методист**: составляет план курса (`course_plan.md`), 
детальный план (`detailed_plan.md`), проверяет соответствие статей плану. 
В детальном плане формулирует ключевые тезисы как конкретные действия, а не абстрактные идеи.
- **Автор**: пишет тексты статей по плану, соблюдая структуру, стиль, объём и 
требования к практичности из раздела «Критерии качества».
- **Редактор/Факт-чекер**: вычитывает статьи, проверяет факты, объём, стиль, 
отсутствие противоречий. Вычёркивает абстрактные советы и статистические данные, 
требует заменить их конкретными шагами.

## Порядок этапов

1. Прочитать этот README и `progress.json` (если файл существует).
2. Создать план курса (`course_plan.md`): 2 модуля, 3 урока, 2 статьи на урок = 12 статей.
3. Создать детальный план (`detailed_plan.md`): для каждой статьи указать тему, 
цель, ключевые тезисы.
4. Пройтись по детальному плану и поправить заголовки и подзаголовки.
   Правила составления подзаголовков H2 и H3 на основе детального плана (`detailed_plan.md`):
   - Заголовок должен полностью пересказывать суть абзаца (блока). 
Читатель должен понять, что узнает, кликнув на него.
   - Используй синоним ключевого слова, отличный от основного.
   - Пиши конкретно: что делать, как работает, какой результат.
   - Не используй общие формулировки: «важность», «правильный подход», 
«раздел первый», абстрактные выражения и сравнения.
   - Выведи один вариант без пояснений, изменения сохрани в детальном плане.
5. Генерировать статьи по порядку (A1, A2, … A12) на основе детального плана. 
Каждую статью сохранять в папку `articles/` в файл с соответствующим именем.
6. После генерации первых 3 статей — остановиться и запросить ручное подтверждение.
7. После подтверждения — продолжить генерацию остальных статей с автопроверкой.
8. Финальная проверка всех статей (вычитка, стиль, согласованность, 
соответствие детальному плану, практическая применимость).

## Критерии качества

- Объём: 3000–3500 символов на статью.
- Стиль: дружелюбный, без жаргона, для новичков.
- Формат: Markdown, заголовки H2/H3, списки, примеры.
- Факты: только из официальных источников (ЦБ РФ, Минфин), как нормы и правила. 
Статистические данные из этих источников не используются.
- Каждая статья содержит: введение, основную часть, вывод.
- Нет противоречий с предыдущими статьями.

### Практичность: как писать, чтобы советы работали

Каждая рекомендация должна быть выполнимой: читатель после статьи может сделать 
конкретное действие и знает, какой результат это даст.

1. **Формат «ситуация → действие → результат».** Указывай, в каком случае что делать и 
что это даст. 
Пример: «Если вам звонят „из банка“ и просят назвать код из СМС — 
положите трубку, сами наберите номер с обратной стороны карты и 
спросите оператора, нужен ли им этот код».
2. **Проверка «можно ли сделать прямо сейчас?».
** Если совет звучит как «будьте внимательны», «следите за расходами», 
«грамотно планируйте» 
— это абстракция. Замени на алгоритм: 
какие действия, в каком порядке, где (раздел приложения банка, документ), что сказать или спросить.
3. **Чек-листы и скрипты.** Составляй списки шагов, перечни документов, скрипты коротких диалогов. 
Пример: «Спросите у продавца три вопроса: какая полная стоимость кредита, 
какой срок кредита, что будет при досрочном погашении».
4. **Числа — только в условных примерах.** Суммы, проценты и сроки можно использовать 
для иллюстрации расчёта и обязательно помечать как «например», «допустим». 
Пример: «Допустим, вы откладываете 5000 ₽ в месяц — за год накопится 60 000 ₽ 
без учёта процентов». Такие примеры не являются данными.
5. **Запрещены любые статистические данные.** Не используй доли населения («80 % россиян»),
 средние значения, данные опросов и исследований, рыночную аналитику, 
«большинство людей», «по статистике». 
Такие данные не нужны: пользу приносит только конкретный алгоритм действий.

### Запрещённые абстрактные формулировки (блок-лист)

- «Важно понимать», «следует помнить», «нужно быть внимательным» — без конкретного действия.
- «Правильный подход к деньгам», «грамотное управление финансами» — без описания, 
что именно делать.
- «Многие люди», «большинство», «по статистике», «в среднем по рынку» — 
обобщения с претензией на данные.
- Числа и проценты, которые выглядят как факт, а не условный пример.

### Автопроверка перед сохранением статьи

Перед сохранением статьи ответь «да» на каждый пункт:

- [ ] В статье есть конкретные шаги (нумерованный список или чек-лист)?
- [ ] Каждый шаг можно начать выполнять без уточнений?
- [ ] Нет статистических утверждений?
- [ ] Нет фраз из блок-листа абстрактных формулировок?
- [ ] Примеры с числами помечены как условные?
- [ ] В конце есть вывод с 1–3 действиями «сделать прямо сейчас»?

## Точки контроля

- После каждого этапа обновлять `progress.json`.
- Если статья не соответствует критериям (включая практичность и запрет статистики) — переписать.
- После генерации первых 3 статей — остановиться и запросить ручное подтверждение.
- Перед финальной проверкой — убедиться, что все статьи сохранены в папке `articles/`.

## Режим работы

- **По умолчанию — автономный.** Если пользователь дал команду «работай автономно» или 
просто «продолжай по README», выполняй все шаги последовательно, 
не запрашивая подтверждение после каждого шага. 
Останавливайся только на точках контроля, указанных выше.
- **Пошаговый режим.** Если пользователь явно просит «выполни только этап X и 
жди подтверждения», выполняй один шаг и жди следующей команды. 
В этом режиме не переходи к следующему этапу без запроса.
